## Q1. Policy enforcement and synthesis for agents (Progent, AgentSpec, Invariant, CaMeL, FIDES, Conseca, ShieldAgent, GuardAgent, AGrail, LlamaFirewall, NeMo, newer)

### Takeaway
The strongest results come from a split design. An LLM (or a person) writes a policy from **trusted context only**: the user task, tool docs and environment facts. A **deterministic checker** then enforces it on each tool call: argument regexes, JSON-schema/SMT rules, or information-flow labels. Progent, Conseca, CaMeL, FIDES and AgentArmor all report AgentDojo attack success near 0–3% with small utility loss. Purely LLM-judged guardrails (ShieldAgent, GuardAgent, AGrail, AlignmentCheck) are more flexible but probabilistic and costlier.

### Cited Findings

**Progent (UC Berkeley, Dawn Song group)**
- VERIFIED: arXiv 2504.11703. v1 16 Apr 2025, v2 30 Aug 2025, v3 14 May 2026. Authors: Shi, He, Wang, Li, Wu, Guo, Song. No venue on the abs page. — [arXiv](https://arxiv.org/abs/2504.11703)
- VERIFIED: How it works. Symbolic rules over tool names and arguments are checked deterministically per call. An LLM writes the initial policy from the user task and proposes updates during execution. A Z3 SMT solver classifies each update: a narrowing is applied automatically, an expansion needs explicit approval. The authors call this "monotonic confinement". — [arXiv abs](https://arxiv.org/abs/2504.11703)
- VERIFIED: Policy language. A list of allow/forbid rules, each with a target tool and argument conditions (comparisons, `in`, regex `match`, `.length`, member access, and/or/not). Rules are implemented as JSON Schema and checked with the `jsonschema` library. Fallbacks: terminate, ask the user, or return an error to the agent. Calls that match no rule are blocked by default. — [arXiv HTML](https://arxiv.org/html/2504.11703)
- VERIFIED: Results.
  - AgentDojo ASR: 39.9% with no defense, 1.0% with Progent, 2.5% with the initial LLM-generated policy alone.
  - ASB ASR: 70.3% → 3.9%, and 0% with manually refined policies.
  - ASR stays below 5% across all policy LLMs tested (1% with the best).
  - Agent model claude-sonnet-4: 6.8% → 0.5%. Meta-SecAlign-70B: 4.8% → 0.3%.
  - About 1% ASR with LangChain, the OpenAI Agents SDK and OpenHands.
  - Defends more than 95% of successful attacks in AutoGen multi-agent runs.
  - Utility is "maintained", but exact figures are only in figures I could not read. — [arXiv HTML](https://arxiv.org/html/2504.11703)
- VERIFIED: Stated limitations. Users approving unsafe expansions. Attacks that stay inside task-needed privilege (e.g. preference manipulation). Attacks that only change text output. GUI agents. "Proxy mode cannot protect built-in tools that bypass MCP interfaces." — [arXiv HTML](https://arxiv.org/html/2504.11703)
- VERIFIED: Code is at github.com/sunblaze-ucb/progent, MIT license, 4 commits. The repo is mostly experiment reproduction (AgentDojo, ASB, an `agentdojo-mcp` folder). — [GitHub](https://github.com/sunblaze-ucb/progent)

**AgentSpec (SMU)**
- VERIFIED: arXiv 2503.18666 (v1 24 Mar 2025, v3 31 Jul 2025). Wang, Poskitt, Sun. Published at ICSE 2026, pp. 2938–2950, DOI 10.1145/3744916.3764546. — [arXiv](https://arxiv.org/abs/2503.18666)
- VERIFIED: A DSL of rules, each made of a trigger, predicates (`check`) and an enforcement. Example: `rule @check_shell_exec trigger PythonREPL check is_destructive enforce user_inspection end`. Enforcement actions are `stop`, `user_inspection` (ask the user), `invoke_action(tool,input)` (substitute a safe action) and `llm_self_examine`. Integrates with LangChain. — [GitHub haoyuwang99/AgentSpec](https://github.com/haoyuwang99/AgentSpec)
- VERIFIED: Results.
  - Prevents unsafe executions in ">90%" of code-agent cases.
  - Eliminates all hazardous actions in the embodied tasks; 100% compliance for autonomous vehicles.
  - Rules generated by an LLM (OpenAI o1): 95.56% precision and 70.96% recall for embodied agents; 87.26% for risky-code identification; prevents law-breaking in 5 of 8 AV scenarios.
  - Overhead "in milliseconds". — [arXiv](https://arxiv.org/abs/2503.18666)
- VERIFIED: No license is shown on the GitHub page (62 stars). — [GitHub](https://github.com/haoyuwang99/AgentSpec)

**CaMeL (Google DeepMind / Google / ETH)**
- VERIFIED: arXiv 2503.18813 (v1 24 Mar 2025, v2 24 Jun 2025). Debenedetti, Shumailov, Fan, Hayes, Carlini, Fabian, Kern, Shi, Terzis, Tramèr. — [arXiv](https://arxiv.org/abs/2503.18813)
- VERIFIED: How it works. Control and data flow are extracted from the trusted user query, so untrusted data cannot change program flow. Capabilities on values plus security policies checked at tool-call time prevent exfiltration. On AgentDojo it solves 77% of tasks "with provable security" versus 84% undefended. — [arXiv](https://arxiv.org/abs/2503.18813)
- VERIFIED: Code at github.com/google-research/camel-prompt-injection, Apache-2.0. It is a research artifact: "The interpreter implementation likely contains bugs". It is not a Google product and there are no plans for support or maintenance. — [GitHub](https://github.com/google-research/camel-prompt-injection)

**FIDES (Microsoft Research)**
- VERIFIED: arXiv 2505.23643 (v1 29 May 2025, v2 3 Sep 2025). Costa, Köpf, Kolluri, Paverd, Russinovich, Salem, Tople, Wutschitz, Zanella-Béguelin. A formal model of agent planners plus a taxonomy of which tasks dynamic taint-tracking can support. — [arXiv](https://arxiv.org/abs/2505.23643)
- VERIFIED: Labels.
  - Confidentiality: {Low, High} or sets of readers (join = intersection). Integrity: {Trusted, Untrusted} or sets of writers (join = union).
  - Tool results whose label is more restrictive than the context are stored in fresh variables. The planner passes them by reference, so the context label stays clean.
  - `query_llm` runs an isolated LLM with a constrained output schema; `inspect` reveals a value.
  - Fides uses two generic policies, where CaMeL uses per-tool policies. — [arXiv HTML](https://arxiv.org/html/2505.23643)
- VERIFIED: Results (AgentDojo, gpt-4o, 949 "Tool Knowledge" attacks).
  - Successful injections: Basic planner 163; Fides without policy checks 24; Fides with policy checks 1, which becomes 0 after excluding two tasks the authors do not count as attacks.
  - With policy checks, Basic loses up to 40 utility points (gpt-4o) and Fides loses up to 24.5 (o3, o4-mini). Fides beats Basic on every model by up to 16.7 points (o1).
  - Models tested: gpt-4o, o1, o3, o4-mini, grok-3.
  - The extracted text had garbled counts; the benchmark appears to be 97 user tasks, 35 injection tasks and 4 environments. — [arXiv HTML](https://arxiv.org/html/2505.23643)
- VERIFIED: Limitations. Text-only injections are not blocked. Some side-effect attacks pass the policy checks. Implicit flows are not prevented. Non-reasoning models misuse `query_llm`. It depends on trusted tool wrappers. Code and tutorial: github.com/microsoft/fides (license not checked). — [arXiv HTML](https://arxiv.org/html/2505.23643)

**Conseca (contextual security policies per task)**
- VERIFIED: arXiv 2501.17070 (v3 17 Apr 2025). Lillian Tsai, Eugene Bagdasarian. HotOS 2025. — [arXiv](https://arxiv.org/abs/2501.17070)
- VERIFIED: How it works.
  - The policy LLM sees only the task plus developer-designated trusted context: email categories and addresses, usernames, the directory tree with file names, time and date, and tool docs. It never sees untrusted content such as email bodies.
  - The policy is, per tool API: whether the call may run at all, regex constraints on arguments, and a human-readable rationale.
  - Enforcement is deterministic `is_allowed(cmd, policy)`. A denial returns the rationale to the planner; the agent gives up after up to 10 failures.
  - Prototype: Gemini 1.5 Pro on a Linux computer-use agent with file and email tools. Over 20 tasks × 5 trials:

    | Policy | Tasks completed (of 20) | Inappropriate actions |
    |---|---|---|
    | No policy | 14.0 | not denied |
    | Static permissive | 12.2 | not denied |
    | Static restrictive | 0.0 | denied |
    | Conseca | 12.0 | denied |

  - The authors call these preliminary results on small synthetic tasks. No code release is stated. — [arXiv HTML](https://arxiv.org/html/2501.17070)

A flow operator `->` matches sequences, for example `get_inbox` followed by `send_email` to an external domain. It has stdlib detectors such as `prompt_injection` with a threshold.

  - It **sends tool names, descriptions and configs to a remote Agent Scan API**. Secrets are said to be redacted. It needs `SNYK_TOKEN`. External contributions are not accepted. — [GitHub](https://github.com/snyk/agent-scan)

**ShieldAgent**
- VERIFIED: arXiv 2503.22738 (v1 26 Mar 2025, v2 27 Nov 2025). Zhaorun Chen, Mintong Kang, Bo Li.

  - ShieldAgent-Bench: 3K instruction/trajectory pairs across 6 web environments and 7 risk categories.

**LlamaFirewall (Meta PurpleLlama)**
- VERIFIED: arXiv 2505.03574 (6 May 2025). Chennabasappa et al. (19 authors). — [arXiv](https://arxiv.org/abs/2505.03574)

### Inferences
- **Fit for per-request use in an ACP client**, which sees one tool-call permission request at a time:
  - **Good fit:** Progent-style or Conseca-style **deterministic policy checks**. They take the tool name and arguments and run in milliseconds. The policy can be generated once per session or turn from trusted inputs: the user prompt, the repo, and tool docs. Progent's "narrowing auto-applies, expansion needs approval" maps naturally onto ACP's allow_once / allow_always / reject options.
  - **Good fit:** AgentSpec rules, Invariant `LocalPolicy` and CodeShield. These are local, ms-scale checks on a single action (Invariant flow rules also need the session history, which a client can keep).
  - **Possible but costlier:** LLM judges (AlignmentCheck, ShieldAgent, GuardAgent, AGrail). They add seconds of latency and per-call cost, and AlignmentCheck needs the agent's reasoning, which an ACP client may not receive.
  - **Not drop-in:** CaMeL, FIDES and AgentArmor (full trace or PDG). They need to control the planner or see data provenance across tool results. CaMeL and FIDES require owning the agent loop, which an ACP client watching a third-party harness does not. AgentArmor needs tool results and their data flow, which a client only partially observes through ACP tool-call updates.
- Snyk Agent Scan is an install-time configuration scanner, not a per-request decision engine, and it phones home. Invariant Guardrails' local mode is the only Invariant piece that fits offline per-request use.

## Q2. Classifiers and judges for actions: benchmarks, FP/FN tradeoffs, monitoring

### Takeaway
The most directly relevant published numbers come from Anthropic's Claude Code **auto mode** (March 2026). It is a two-stage Sonnet 4.6 transcript classifier that sees only user messages and tool calls. It reports **0.4% FPR on 10,000 real calls but 17% FNR on 52 real "overeager" actions**. The misses are mostly about judging whether the user's consent covered the action's blast radius. OpenAI Codex ships a comparable "auto-review" reviewer agent. Academic risk benchmarks (ToolEmu, R-Judge, AgentHarm, AgentDojo) mostly predate coding-specific approval gating. New 2026 benchmarks such as AuthGateBench target it directly but report models over-blocking authorized actions.

### Cited Findings

**Industry action classifiers**
- VERIFIED: Anthropic, "Claude Code auto mode" engineering post, 25 Mar 2026. — [Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)
  - **Motivation:** users approve 93% of permission prompts.
  - **Inputs:** a server-side prompt-injection probe scans tool outputs and adds warnings for the main agent. A transcript classifier on **Sonnet 4.6** sees **only user messages and the agent's tool calls**. Assistant text and tool results are stripped, so it is "reasoning-blind" by design, to stop persuasion by the agent and injection through tool output.
  - **Stages:** Stage 1 is a single-token yes/no check told to "err on the side of blocking". Stage 2 is chain-of-thought reasoning, run only when Stage 1 flags, with a near-identical prompt that is mostly cache hits.
  - **Tiers:** (1) built-in read-only tools plus narrow user allow rules; broad rules such as blanket shell or interpreter wildcards are dropped on entering auto mode. (2) In-project file edits, which are reviewable via VCS. (3) Everything else goes to the classifier.
  - **Prompt template:** fixed, with three slots. Environment/trust boundary (by default only the current git repo is trusted). More than 20 default block rules: destroy/exfiltrate, degrade security posture, cross trust boundaries, bypass review or affect others. Narrow allow exceptions, such as installing packages already in the manifest or pushing to the session branch. `claude auto-mode defaults` prints them.
  - **Fixed rules:** judge real-world impact, treat `&&` chains as one action, and evaluate scripts assembled then executed. User intent is read conservatively: "can we fix this?" is a question, not authorization.
  - **Results:**

    | Configuration | FPR, real traffic (n=10,000) | FNR, real overeager (n=52) | FNR, synthetic exfiltration (n=1,000) |
    |---|---|---|---|
    | Stage 1 only | 8.5% | 6.6% | 1.8% |
    | Full pipeline | 0.4% | 17% | 5.7% |

  - **Ablation:** adding assistant messages and tool results *hurt* on the overeager set. Tool-calls-only had the lowest FNR but blocked requested actions. User messages plus tool calls was best overall.
  - **Deny-and-continue:** a denial goes back to the agent as a tool result. It escalates to the human after 3 consecutive or 20 total denials; headless mode (`claude -p`) terminates instead.
  - **Multi-agent:** delegation to subagents is checked outbound (can deny). Subagent returns are checked and only warn.
  - **Stated limits:** the 17% FNR, mainly around consent scope; the small n=52 set; no provenance for identifiers; not a substitute for human review on high-stakes infrastructure.
- VERIFIED: Product post: auto mode launched 24 Mar 2026 as a research preview and became generally available 10 Jul 2026. It "may still allow some risky actions" and "may occasionally block benign actions". — [Claude blog](https://claude.com/blog/auto-mode)
- UNVERIFIED (secondary): Claude Code made auto mode the default around 14 Aug 2026. — [aiweekly](https://aiweekly.co/alerts/anthropic-flips-claude-code-to-auto-mode-by-default-aug-14), [implicator.ai](https://www.implicator.ai/anthropic-claude-code-auto-mode-default/)
- VERIFIED: OpenAI Codex "auto-review". — [OpenAI/ChatGPT docs](https://learn.chatgpt.com/docs/sandboxing/auto-review) (redirected from developers.openai.com/codex/auto-review)
  - Setting `approvals_reviewer = "auto_review"` (with `approval_policy = "on-request"`) makes a reviewer agent decide eligible boundary-crossing requests: escalated shell calls, blocked network, out-of-root edits, and MCP/app calls.
  - It sees a compact transcript: user messages, surfaced assistant updates, relevant tool calls *and outputs*, and the proposed action. It does not see private chain-of-thought.
  - It "does not expand `writable_roots`, enable network access, or weaken protected paths" ("a reviewer swap, not a permission grant").
  - Circuit breaker: 3 consecutive denials, or 10 denials in the last 50 reviews. The `/approve` command allows one retry of a recent denied action.
  - The docs say it is "not a deterministic security guarantee". No accuracy numbers are published.
  - Policies are set with `[auto_review].policy` or managed `guardian_policy_config`.
- UNVERIFIED (secondary blogs): an earlier Codex config value was `guardian_subagent`, and the feature appeared in v0.115.0. Codex also has Starlark command rules and prefix-rule "smart approvals". — [danielvaughan.com](https://codex.danielvaughan.com/2026/03/30/codex-cli-rules-engine-starlark-smart-approvals)

**AI control and monitoring**
- VERIFIED: Ctrl-Z (Redwood Research), arXiv 2504.10374 (14 Apr 2025). BashBench: 257 multi-step sysadmin tasks. "Resample protocols" draw extra samples of suspicious actions; the best combines resampling with analysis of previous steps. Attack success falls from 58% to 7% at a 5% cost to benign-agent performance. Site: bashcontrol.com. — [arXiv](https://arxiv.org/abs/2504.10374)
- VERIFIED: "Chain of Thought Monitorability: A New and Fragile Opportunity for AI Safety", arXiv 2507.11473 (Jul 2025; v2 Dec 2025). Korbak, Balesni, … Baker, Shah, Mikulik: a multi-lab author list. CoT monitoring is imperfect but promising, and developers should preserve monitorability. — [arXiv](https://arxiv.org/abs/2507.11473)
- UNVERIFIED (not fetched): the original AI Control paper on trusted monitoring/editing, Greenblatt et al., arXiv 2312.06942 (Dec 2023). — [arXiv](https://arxiv.org/abs/2312.06942)

### Inferences
- Anthropic's design choices bear directly on a client-side gate:
  - Strip agent prose and tool output from the judge's input (anti-persuasion, anti-injection).
  - Keep the user's messages as the intent anchor.
  - Use a cheap high-recall stage then an expensive stage on flags.
  - Use deny-and-continue with escalation counters.
- An ACP client sees the user prompt it sent and each tool call's title, kind and raw input, so it can rebuild roughly the "user messages + tool calls" view the auto mode classifier uses. This is the configuration Anthropic found best.
- The consistent weak spot across Anthropic's FNR analysis, AuthGateBench, and the Ting Yan user study (Q4) is **consent scope**: whether a vague request authorizes this blast radius. It is not recognizing that an action is dangerous. Repo-derived context (what is "ours" vs shared, which branch belongs to the session) is the input that AuthGateBench says helps.
- Stage 1 alone (8.5% FPR) would mean roughly 1 in 12 actions blocked. On long coding sessions that is likely too noisy without deny-and-continue.

### Gaps
- No public FPR/FNR numbers for Codex auto-review were found.
- AuthGateBench per-model numbers were not read (abstract only).
- I found no open-source, verified terminal-command risk dataset with labeled benign vs dangerous commands and published classifier precision/recall. The candidates (Saber, InfraBench, the malicious-skills benchmark) are unverified snippets.
- Not covered: SHADE-Arena, OpenAI's CoT-monitoring paper (Baker et al.), and the Redwood/Anthropic monitoring posts beyond Ctrl-Z.

## Q3. Deriving permissions from the code/project, task-scoped least privilege, learning from approval history

### Takeaway
Task-scoped least privilege is well represented: Conseca, Progent, MiniScope and intent-governed authorization all derive a policy from the task plus trusted environment context. Conseca explicitly feeds the **directory tree and file names** to the policy generator. Learning from approval history has one strong result: Wu et al., IEEE S&P 2026, 85.1% prediction accuracy with history versus 66.9% without. I found **no** published work that uses a code graph, call graph, or build/test metadata to scope a coding agent's permissions. That looks like an open gap.

### Cited Findings
- VERIFIED: Conseca's trusted context for policy generation includes "the filesystem directory tree, including file and directory names", user and email metadata, and tool docs. Policies are regex constraints on arguments per tool, each with a rationale. — [arXiv HTML 2501.17070](https://arxiv.org/html/2501.17070)
- VERIFIED: Progent generates the initial policy from the user task with an LLM and gates later expansions via SMT plus approval. — [arXiv 2504.11703](https://arxiv.org/abs/2504.11703)
- VERIFIED: MiniScope automates discovery of a task-centric permission hierarchy and cuts confirmations by 43.4–89.4%. — [arXiv 2512.11147](https://arxiv.org/abs/2512.11147)
- VERIFIED: Claude Code auto mode's template has an "Environment" slot that defines the trust boundary (by default only the current git repo). Allow exceptions include "installing packages already in the repo manifest" and pushing to the session's branch. These are repo-derived signals used as classifier context. — [Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)
- VERIFIED: "Towards Automating Data Access Permissions in AI Agents" (Wu, Yang, Roesner, Kohno, Zhang, Iqbal), arXiv 2511.17959 (22 Nov 2025), IEEE S&P 2026.
  - A user study identified the factors behind permission decisions. An ML assistant then predicts future decisions using permission history.
  - Accuracy: 85.1% overall, 94.4% on high-confidence predictions, 66.9% without history. 1–4 training samples add 10.8%.
  - The study size and code were not shown on the abs page. — [arXiv](https://arxiv.org/abs/2511.17959)
- UNVERIFIED (search snippet): "Reframing…" (2605.24309) proposes preference learning from approval histories that generalizes across similar actions and decays over time, unlike fixed "always allow". — [arXiv HTML](https://arxiv.org/html/2605.24309v1)
- UNVERIFIED (search snippets): Codex "smart approvals" learn or suggest prefix rules from approvals. — [danielvaughan.com](https://codex.danielvaughan.com/2026/05/04/codex-cli-smart-approvals-adaptive-command-policies-prefix-rules/)
- UNVERIFIED (search snippets): "Investigating Over-Privileged Tool Selection in LLM Agents" (2606.20023) studies least-privilege tool choice and fine-tunes on it. — [arXiv](https://arxiv.org/pdf/2606.20023)
- UNVERIFIED (search snippets): Sandlock (2605.26298) splits sandbox policy into static rules (path prefixes, ports, syscalls) and runtime decisions (connect destinations, execve argv). — [arXiv](https://arxiv.org/pdf/2605.26298)
- UNVERIFIED (search snippets): "Permission Denied: Policy-Graded Evaluation of Coding Agents in Hardened Environments" (2608.02670) runs pre-flight probes and fails closed. — [arXiv](https://arxiv.org/pdf/2608.02670)

### Inferences
- A repo-aware gate could feed a Conseca/Progent-style policy generator with trusted, non-LLM-derived repo facts:
  - the file and module list and ownership (code graph),
  - test and build commands (from manifests and CI config),
  - declared dependencies (package manifests),
  - git remotes and the current branch,
  - endpoints referenced in code or config.
  This is a plausible novel slice. Hobbes's extraction (`graph.json`, `tests.json`, `interfaces.json`) already produces some of these inputs, but which fields would map to permissions is untested and unverified.
- Approval-history learning (Wu et al.) fits a client that records each ACP permission decision. The result is from data-access permissions in general agents, not shell commands in coding agents, so transfer is unverified.
- Learned "allow_always" rules carry the allowlist risks in Q4 (environment poisoning, alternative paths). Anthropic drops broad interpreter or shell rules on entering auto mode for this reason.

### Gaps
- No paper found that uses static analysis, call graphs, or build/test metadata to infer a coding agent's allowed commands, files, or network endpoints. One targeted search found only general sandboxing material. This is either an unexplored gap or something my searches missed.
- Wu et al.'s participant count, features and model type were not extracted.

## Q4. Known attacks on approval systems: injection-caused approvals, approval fatigue, obfuscation and evasion

### Takeaway
Command allowlists are repeatedly bypassed because they judge the surface command, not what the shell will execute in a possibly poisoned environment. CVE-2026-22708 in Cursor is the canonical case. Prompt injection has been used to flip harnesses into auto-approve, and auto-approve raises attack success to about 96% in HarnessSecurity-Bench. Approval fatigue is real: 93% of prompts are approved in Claude Code. A 2026 user study found that user-written policies blocked *less* overreach than per-action human or automated review.

### Cited Findings
- VERIFIED: **CVE-2026-22708 (Cursor)**, Pillar Security, published 14 Jan 2026. — [Pillar Security](https://www.pillar.security/blog/the-agent-security-paradox-when-trusted-commands-in-cursor-become-attack-vectors)
  - Shell built-ins (`export`, `typeset`, `declare`) ran without approval even with an empty allowlist. They poison environment variables so that allowlisted commands execute attacker code: `PAGER` makes `git branch` run it, and `PYTHONWARNINGS`/`BROWSER`/`PERL5OPT` chains turn `python3` into code execution.
  - Zero-click variants write to `~/.zshrc` via here-strings with redirection.
  - Cursor's January 2026 fix requires approval for commands its server-side parser cannot classify. Cursor itself says the allowlist is "not a security guarantee".
- UNVERIFIED (search snippets):
  - CVE-2025-62222: injected text edits `.vscode/settings.json` to enable auto-approval of terminal commands in GitHub Copilot.
  - CVE-2025-65099: a poisoned project config runs code before Claude Code's trust dialog.
  - CVE-2026-22179: command substitution inside double quotes bypassed an allowlist in OpenClaw.
  - Substring-based allowlist matching bypassed by hiding a command behind a comment.
  — [arXiv 2601.17548](https://arxiv.org/pdf/2601.17548), [DEV Community](https://dev.to/darkaxiom/why-command-allowlists-dont-protect-your-ai-coding-agent-68i), [arXiv 2608.05201](https://arxiv.org/pdf/2608.05201)
- VERIFIED: HarnessSecurity-Bench. Auto-approve takes ASR from 29.2% to 95.6%. "Allowed tools or commands can leave unauthorized operations reachable through alternative execution paths." — [arXiv 2610.07639](https://arxiv.org/abs/2610.07639)
- VERIFIED: Claude Code users approve 93% of permission prompts. In auto mode, synthetic exfiltration attempts ("often obfuscated", n=1,000) still get through at 5.7% FNR with the full pipeline. The classifier evaluates assembled-then-executed scripts and `&&` chains as single actions specifically to resist evasion. — [Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)
- VERIFIED: Ting Yan, "Do User-Authored Permission Policies Improve Protection Against AI Agent Overreach?", arXiv 2608.27443 (27 Aug 2026), with 113 non-developer participants. — [arXiv](https://arxiv.org/abs/2608.27443)
  - Conditions: per-action human approval (HITL), automated per-action review (AUTO), and user-written rules (POLICY). The simulated day had 18 actions, 7 of them overreach.
  - POLICY blocked 20.1 percentage points less overreach than HITL (95% CI [−32.1, −8.1]) and 14.5 points less than AUTO (95% CI [−25.8, −3.2]).
  - POLICY reduced prompts from 18.0 to 10.9.
  - Under POLICY, 133 of 148 executed overreach actions ran *after human approval*. Users chose "ask" for 114 of 140 rules.
- VERIFIED: LlamaFirewall notes that the LLM auditor (AlignmentCheck) can itself be prompt-injected. It mitigates this by restricting the auditor's inputs and pre-scanning with PromptGuard. — [arXiv HTML 2505.03574](https://arxiv.org/html/2505.03574)
- VERIFIED: Progent lists user mistakes in approving unsafe expansions as a limitation, along with attacks that stay within task-needed privilege. — [arXiv HTML 2504.11703](https://arxiv.org/html/2504.11703)
- VERIFIED: "How Agentic AI Coding Assistants Become the Attacker's Shell" (Liu, Zhao, Lyu, Zhang, Wang, Lo), arXiv 2605.25871 (May 2026). Hidden instructions in external artifacts hijack coding assistants. The abstract gives no numbers. — [arXiv](https://arxiv.org/abs/2605.25871)

### Inferences
- A per-request gate should parse commands as the shell would (built-ins, env assignments, substitutions, redirections, here-strings) or treat anything unparseable as needing review, as Cursor's fix does. Prefix or substring allowlists are not adequate.
- An LLM judge must not see untrusted tool output, or it inherits the injection surface. Anthropic's stripping and LlamaFirewall's input restriction both reflect this.
- "Allow always" in ACP is exactly the persistent-rule mechanism these attacks exploit. A client should probably scope or expire it rather than store broad rules. This is a design suggestion, not a tested result.

### Gaps
- No quantified measurement of approval fatigue as decision quality over time (rather than approval rate) was found. Ting Yan does not measure fatigue directly.
- The snippet-sourced CVE details (62222, 65099, 22179) were not verified on NVD or vendor advisories.
- No published evasion study against Claude Code auto mode or Codex auto-review specifically was found. Backslash Security has a blog post titled "auto mode catches a lot but not everything", which was not read. — [Backslash](https://www.backslash.security/blog/claude-code-auto-mode-catches-a-lot-but-not-everything)
