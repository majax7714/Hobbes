# Harnesses pre-decide most actions before clients ask

> Research for the permission-wiring decision (DEC-007). Snapshot as of
> **2026-10-16**, by research subagents from vendor docs, source code,
> advisories and papers. Versions and products change quickly, so re-verify
> before relying on a detail. The cited source notes are in
> `coding-agent-auto-permissions-notes/`.

By October 2026 the major coding-agent vendors have settled on the same layered pipeline for "auto permissions." Deterministic rules and built-in read-only lists go first. An OS sandbox comes next, and fitting inside it is itself the main auto-approval criterion for shell. An LLM judge reviews whatever is left: Claude Code auto mode, Codex Auto-review, Cursor Auto-review, VS Code "Assisted permissions." A human sees only what the judge cannot settle. Every major vendor that ships a judge disclaims it in its own docs: Cursor and VS Code call theirs "not a security boundary," OpenAI calls Auto-review "not a deterministic security guarantee," and Anthropic says auto mode is no substitute for careful human review on high-stakes infrastructure. The only published error rates come from Anthropic: 0.4% false positives on real traffic and 17% false negatives on real "overeager" actions. Nothing in the surveyed products or literature derives permissions from code structure. "Codebase-aware" in practice means reading CLAUDE.md, README, git remotes, `package.json` script names or past transcripts. The public bypasses fall into two families, and both point to where a repo code graph could help: checkers that match command text instead of resolving what will execute, and harnesses that trust repo-controlled config such as git hooks, `core.fsmonitor`, `.env` and project settings. For an ACP client like Hobbes, the binding constraint is structural. Each harness decides most actions internally before any `session/request_permission` is sent. Codex's ACP adapter defaults to its own reviewer model. Gemini sends no raw command input. Hobbes's client currently drops the tool kind and raw input from each request and never sets a mode. What follows lays out the mechanisms, inputs, failure modes and replicability for each player, then the options a graph-informed policy opens up. Throughout, "verified" means the research notes confirmed the claim in official docs, source code, changelogs or advisories, and "unverified" marks blogs, press, reverse engineering or inference.

## Claude Code, Codex and Gemini stack rules, sandbox and judge differently

The three harnesses that Hobbes drives share the layered shape but put the weight in different places. Claude Code relies most on a transcript classifier, Codex on the OS sandbox plus a reviewer agent, and Gemini on a priority-ordered rule engine with pluggable checkers.

| | Claude Code (2.1.296 local) | Codex CLI (0.163.0 source; 0.160.1 local) | Gemini CLI (v0.64.0) |
|---|---|---|---|
| Static rules | `allow/ask/deny` in settings, deny-first; Bash split per subcommand | Starlark `prefix_rule` (allow/prompt/forbidden), strictest wins | TOML rules with priority tiers, highest wins |
| Sandbox role | Opt-in; sandboxed Bash auto-approved even in Manual mode | Default; in-sandbox commands never prompt | Opt-in; approvals independent of sandbox |
| Model judge | Auto mode classifier (default in interactive terminal since v2.1.283) | Auto-review reviewer agent (opt-in in CLI, **default in codex-acp**) | Conseca (opt-in, fails open) |
| Learned rules | Per-prompt prefix suggestions; transcript-mining skill | Model-proposed prefix amendment, banned-prefix list | Session "always" rule; optional `auto-saved.toml` |
| Repo-derived input | CLAUDE.md and git remotes to classifier; `/auto-mode-setup` reads README/config | None structural; `AGENTS.md` trusted by reviewer | Last user prompt + tool declarations to Conseca |

### Claude Code: a reasoning-blind classifier behind deny-first text rules

Claude Code has six permission modes (`default`/Manual, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`). **Since v2.1.283, auto is the built-in default for interactive terminal and VS Code sessions** but not for `claude -p` or Agent SDK sessions that fetch feature flags (verified) ([Permission modes](https://code.claude.com/docs/en/permission-modes)). In auto mode, explicit allow/ask/deny rules resolve first. Read-only actions and file edits inside the working directory are then auto-approved **without classifier review** in client-side mode. Everything else goes to the classifier: shell, network, MCP, out-of-repo writes and subagent spawns. A block returns a reason such as `[Data Exfiltration]` to the agent (verified) ([Permission modes](https://code.claude.com/docs/en/permission-modes)). The classifier sees user messages, non-read-only tool calls and CLAUDE.md. **Tool results and assistant prose are stripped** as an injection and persuasion defense. Before `git reset --hard` or `rm -rf`, Claude Code runs `git status` itself so the classifier knows whether uncommitted work exists (verified) ([Permission modes](https://code.claude.com/docs/en/permission-modes)).

Anthropic's March 2026 engineering post describes two stages: a single-token filter biased toward blocking, then chain-of-thought re-evaluation only on flags. The post was motivated by users approving **93% of permission prompts** (verified) ([Anthropic engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)). Its evaluation is the only real-traffic error data any vendor has published:

| Dataset | Stage 1 | Full pipeline |
|---|---|---|
| Real internal traffic, n=10,000 (false-positive rate) | 8.5% | 0.4% |
| Real overeager actions, n=52 (false-negative rate) | 6.6% | 17% |
| Synthetic exfiltration, n=1,000 (false-negative rate) | 1.8% | 5.7% |

Anthropic calls 17% "the honest number" and attributes most misses to **consent mismatch**: the classifier saw the danger but misjudged whether the user's earlier words authorized it. An ablation found that adding assistant messages and tool results made overeager detection worse ([Anthropic engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)). The classifier applies about 40 built-in prose categories (blocking `curl | bash`, force push, `terraform destroy`, IAM grants, commenting out security tests, `rm -rf "$VAR"` with an unseen `$VAR`) plus user `autoMode.environment/allow/soft_deny/hard_deny` entries. **`autoMode` is read only from user, managed or CLI settings, never from project settings, specifically to block repo injection.** The same rule ignores `"auto"` or `"bypassPermissions"` in a checked-in `.claude/settings.json` (verified) ([Configure auto mode](https://code.claude.com/docs/en/auto-mode-config); [Permission modes](https://code.claude.com/docs/en/permission-modes)). On entering auto mode, broad allow rules such as `Bash(*)`, interpreter wildcards and package-manager run commands are dropped. After 3 consecutive or 20 total blocks, auto mode pauses and falls back to prompting.

Several sources conflict. The engineering post named Sonnet 4.6 as the classifier and said headless runs "terminate" at the block threshold. Current docs name Sonnet 5 by default and say the run continues ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Anthropic's product post gives research preview on 24 March 2026 and general availability on 10 July 2026 ([Claude blog](https://claude.com/blog/auto-mode)). A secondary report puts default-on for Pro/Max/Team at 14 August 2026, with "humans catch 13.6% vs classifier 89%" figures that appear in no Anthropic source (unverified) ([aiweekly](https://aiweekly.co/node/9487)). No error rates have been published for the current classifier model.

The static rule layer is explicitly not a boundary. Rules are evaluated deny, then ask, then allow, regardless of specificity. Bash commands are split on `&&`, `||`, `;`, `|`, `&` and newlines. A fixed wrapper list (`timeout`, `nice`, `nohup`, bare `xargs`) is stripped, but `direnv exec`, `devbox run`, `npx` and `docker exec` are not, so `Bash(devbox run *)` matches `devbox run rm -rf .`. **The docs state that `Bash(rm *)` does not stop `/bin/rm` or `bash -c 'rm …'`, and that `Bash(git push *)` does not stop `git -C . push`.** A deny rule "isn't a security boundary around the program" (verified) ([Permissions docs](https://code.claude.com/docs/en/permissions)). Anthropic directs real enforcement to the opt-in sandbox (bubblewrap on Linux, Seatbelt on macOS). It confines writes to the working directory, leaves reads open to "most of the machine, including credential files such as `~/.ssh`", and routes network through a proxy whose allowlist starts empty. **Sandboxed commands run with no prompt even in Manual mode.** Anthropic reported an 84% prompt reduction in October 2025 internal use (verified) ([Sandboxing docs](https://code.claude.com/docs/en/sandboxing); [Anthropic engineering: sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)). The agent can retry outside the sandbox with `dangerouslyDisableSandbox`. Only `allowUnsandboxedCommands: false` closes that path.

On the question of whether anything is generated from the codebase: **no mechanism analyzes code structure (imports, call graph, test layout) to derive rules.** The "codebase-aware" impression comes from four sources. First, per-prompt "don't ask again" suggestions: per-subcommand prefixes, at most 5 rules, editable in the TUI ([Permissions docs](https://code.claude.com/docs/en/permissions)). Second, the bundled `/fewer-permission-prompts` skill, which mines recent transcripts for frequent read-only Bash and MCP calls and writes an allowlist to the project's `.claude/settings.json` (verified) ([Commands docs](https://code.claude.com/docs/en/commands)). A third-party blog gives thresholds of 50 sessions, 3 or more occurrences and the top 20 (unverified) ([Classmethod](https://dev.classmethod.jp/en/articles/claude-code-fewer-permission-prompts/)). Third, `/auto-mode-setup`, which reads the project's CLAUDE.md, README, config files, git remotes and the hosts and command names from recent sessions, then drafts `environment` entries into user settings (verified) ([Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)). Fourth, the classifier itself reads CLAUDE.md and session-start git remotes on every check. In 2025, a Haiku "command prefix detection" call chose the prefix and flagged injection (unverified, reverse-engineered) ([xpnsec](https://blog.xpnsec.com/an-evening-with-claude-code/)). Its marker strings were not found in the 2.1.296 binary, so whether a model is still involved is unknown.

### Codex: the sandbox is the boundary; a reviewer agent handles escalations

Codex runs on two orthogonal axes: `approval_policy` (`on-request`, `never`, `granular`) and `sandbox_mode` (`read-only`, `workspace-write`, `danger-full-access`). **In the default `on-request` preset with a restricted sandbox, a non-dangerous command that does not request escalation runs with no prompt, "let[ting] the sandbox enforce restrictions"** (verified) ([exec_policy.rs#L770-L855](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/src/exec_policy.rs#L770-L855)). The Linux sandbox is bubblewrap plus seccomp: Landlock was demoted to legacy and bwrap became the default in March 2026. Network is off by default in `workspace-write`, and `.git`, `.codex`, `.agents` and `.aws` stay read-only inside writable roots (verified) ([Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)). The `untrusted` policy was retired on 20 August 2026. Its strictness moved to a per-project `trust_level = "untrusted"`, which also disables project-local config ([openai/codex#39630](https://github.com/openai/codex/pull/39630)).

OpenAI's 2026 history is the clearest evidence that static "known-safe" lists fail against repo-controlled state. The list was narrowed in May 2026, then **Git was removed because "Repository configuration can cause even read-only Git commands to execute helpers"**, and the whole allowlist was deleted on 20 August 2026 (verified) ([#39524](https://github.com/openai/codex/pull/39524); [#39630](https://github.com/openai/codex/pull/39630)). What remains is a dangerous-command heuristic for forced `rm` that recurses through `sudo`/`env`/`trap`. The shell parser splits only word-only chains and treats redirections, substitutions, globs and control flow as one opaque invocation ([shell-command/src/bash.rs](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/shell-command/src/bash.rs#L22-L135)).

Execution policy uses Starlark `prefix_rule(pattern, decision, justification, match, not_match)`. Rules load from every config layer, with project rules only when the project is trusted, and the strictest match wins. **An `allow` rule runs the command outside the sandbox without prompting**, so a remembered prefix is more powerful than a session approval (verified) ([Rules docs](https://learn.chatgpt.com/docs/agent-configuration/rules); [execpolicy/README.md](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/execpolicy/README.md)). "Learning" works like this: the model proposes a `prefix_rule` during escalation, the user confirms, and Codex appends it to `~/.codex/rules/default.rules`. A `BANNED_PREFIX_SUGGESTIONS` list refuses over-broad prefixes such as `bash`, `python`, `node`, `git`, `rm` and `npm run` ([exec_policy.rs#L57-L146](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/core/src/exec_policy.rs#L57-L146)).

The model judge is **Auto-review**, introduced as "Guardian" and renamed in April 2026. It reviews only eligible requests: shell escalations, blocked network, edits outside writable roots, MCP/app calls that need approval and `request_permissions`. In-sandbox actions are never routed to it (verified) ([Auto-review docs](https://learn.chatgpt.com/docs/sandboxing/auto-review)). Unlike Anthropic's classifier, **it sees tool outputs as well as user messages** and can run read-only probes. Its prompt treats only user/developer messages, `AGENTS.md` and `request_user_input` responses as trusted, and tells it to "resolve any variables or expansions fully at the time of execution" (verified) ([guardian/policy.md](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/prompts/templates/guardian/policy.md); [classifier_instructions.md](https://github.com/openai/codex/blob/rust-v0.163.0/codex-rs/prompts/templates/guardian/classifier_instructions.md)). It outputs a risk level, `user_authorization` and a rationale. It times out at 90 seconds and trips a circuit breaker at 3 consecutive denials or 10 of the last 50 reviews. One docs page says prompt-build, session and parse failures fail closed; the Auto-review page itself does not say so ([Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)). **OpenAI publishes no accuracy numbers** and calls it "not a deterministic security guarantee."

### Gemini: policy as data, with a pluggable checker slot and a fail-open Conseca

Gemini CLI compiles all four approval modes (`default`, `autoEdit`, `plan`, `yolo`) and every legacy setting (`tools.allowed`, `tools.exclude`, `mcpServers.*.trust`) into one TOML policy engine. Priority is `tier + priority/1000`, with tiers default 1, extension 2, workspace 3, user 4 and admin 5 (verified) ([policy/config.ts#L66-L81](https://github.com/google-gemini/gemini-cli/blob/v0.64.0/packages/core/src/policy/config.ts#L66-L81)). The repo's own docs contradict the code: their worked examples use different tier numbers. They also concede that **the workspace (project) tier "is currently non-functional"** (issue #18186, still open) ([policy-engine.md](https://github.com/google-gemini/gemini-cli/blob/v0.64.0/docs/reference/policy-engine.md)). Shell commands are split into sub-commands. Redirection downgrades `allow` to ask, cwd outside the workspace or git in an untrusted folder forces ask, and a hard-coded known-safe list (`cat`, `ls`, `grep`, flag-checked `git`/`find`/`sed`) upgrades ask to allow, **including with no sandbox** (verified) ([policy-engine.ts#L366-L440](https://github.com/google-gemini/gemini-cli/blob/v0.64.0/packages/core/src/policy/policy-engine.ts#L366-L440); [commandSafety.ts](https://github.com/google-gemini/gemini-cli/blob/v0.64.0/packages/core/src/sandbox/utils/commandSafety.ts#L167-L300)).

After rule matching, `[[safety_checker]]` entries run, in-process or external. A checker that throws yields DENY ([policy-engine.ts#L959-L1005](https://github.com/google-gemini/gemini-cli/blob/v0.64.0/packages/core/src/policy/policy-engine.ts#L959-L1005)). One built-in checker is **Conseca**. A policy-generator prompt takes the last user prompt and the tool declarations as trusted input, and emits per-tool allow/deny/ask with constraints. A Flash enforcer model then judges each call against that policy. **Conseca is opt-in and returns ALLOW on missing config, parse errors or enforcement errors, so it fails open internally** even though the engine fails closed on thrown errors (verified) ([conseca.ts](https://github.com/google-gemini/gemini-cli/blob/v0.64.0/packages/core/src/safety/conseca/conseca.ts#L60-L105)). Folder trust is off by default. When enabled, untrusted folders ignore workspace settings, `.env` and MCP servers ([trusted-folders.md](https://github.com/google-gemini/gemini-cli/blob/v0.64.0/docs/cli/trusted-folders.md)). Sandboxing is opt-in, so in the default configuration every auto-allow runs on the host.

## Fourteen other agents: static lists, self-declared risk, or a separate judge

The rest of the field sorts into three tiers. **Static rules only:** Roo, Kilo, Zed, Junie, Warp lists, Windsurf/Devin Desktop lists, and VS Code terminal rules. **The acting model labels its own call:** Cline's legacy `requires_approval` and OpenHands' default `security_risk` field. **A separate judge model:** Cursor, VS Code/Copilot, Goose, OpenHands' optional analyzers and Amp plugins. Cursor and VS Code reached the same design about five months apart: allowlist, sandbox, LLM judge, human. **"Learned" permissions nearly always mean that "always allow" persists a static rule generalized from one approval.** None of the products surveyed trains on approval history.

Two sources disagree about Cline. Its docs say the model flags each command. The 4.1.x SDK bundle's tool schema has no such field, and every command tool maps to one `executeSafeCommands` toggle. That makes "safe" meaningless per command on the SDK path (unverified inference from source) ([Cline source](https://github.com/cline/cline/blob/b549ceb4bb4247284c975f6d6ca0979decec097c/apps/vscode/src/sdk/sdk-tool-policies.ts#L48)). Taken with Cline's admitted no-op toggles, these show that **configured permission controls do not always reach the code path that decides.**

Two designs carry over to Hobbes directly. Goose's read-only judge can be replicated exactly by a client, because its whole input is the tool name and arguments. And Goose is itself an ACP client of Claude, Codex, Amp and Copilot: **for ACP-forwarded requests it applies no judge**, just mapping `Auto` to allow-once and sending `SmartApprove` to the user ([acp/provider.rs#L2375](https://github.com/block/goose/blob/59e588dfd941ae129f2938deb7acf9f80b6edd02/crates/goose/src/acp/provider.rs#L2375)). VS Code, also a multi-harness host, does the same thing in a different form. It exposes each harness's own modes (Codex "Auto-Review," Claude modes) instead of judging their requests itself ([approvals](https://code.visualstudio.com/docs/agents/run/approvals)). No surveyed multi-harness host runs its own policy over forwarded requests. That niche is empty.

## Research splits policy writing from deterministic enforcement

The strongest academic results share one architecture. An LLM or a person writes a narrow policy from **trusted context only**: the user task, tool docs and environment facts, never tool output. A deterministic checker then enforces it on each call. **Progent** generates JSON-Schema rules over tool arguments from the user task and checks updates with Z3: narrowings apply automatically, expansions need approval. It cut AgentDojo attack success from 39.9% to 1.0%, and ASB from 70.3% to 3.9% (verified) ([arXiv 2504.11703](https://arxiv.org/html/2504.11703)). **Conseca** (HotOS 2025), the paper Gemini's checker is named after, feeds the policy LLM the task plus **"the filesystem directory tree, including file and directory names,"** and enforces regex argument constraints deterministically. On 20 small synthetic tasks it completed 12.0, against 12.2 for a static permissive policy, while denying the inappropriate actions that policy let through. The authors call these results preliminary (verified) ([arXiv 2501.17070](https://arxiv.org/html/2501.17070)). CaMeL solves 77% of AgentDojo tasks "with provable security" against 84% undefended ([arXiv 2503.18813](https://arxiv.org/abs/2503.18813)). FIDES cut successful injections from 163 to 1 using information-flow labels ([arXiv 2505.23643](https://arxiv.org/html/2505.23643)). Both CaMeL and FIDES require owning the agent loop, which an ACP client watching a third-party harness does not. MiniScope reports **43.4–89.4% fewer confirmations** than per-tool prompting by discovering task-scoped permission hierarchies (verified) ([arXiv 2512.11147](https://arxiv.org/abs/2512.11147)). AgentSpec offers a trigger/check/enforce rule DSL with millisecond overhead, published at ICSE 2026 ([arXiv 2503.18666](https://arxiv.org/abs/2503.18666)).

Benchmarks of judges and approval systems sharpen the trade-offs. **HarnessSecurity-Bench**, covering Claude Code, Codex CLI, Gemini CLI and Copilot, found that **auto-approve raised attack success from 29.2% to 95.6%**, and that "allowed tools or commands can leave unauthorized operations reachable through alternative execution paths" (verified) ([arXiv 2610.07639](https://arxiv.org/abs/2610.07639)). AuthGateBench treats LLMs as the authorization gate for Claude Code and Codex. Its finding is the reverse failure: models "still block most actions even when explicitly authorized," and **environment signals retrieved after the fact substantially improve accuracy**. Per-model numbers were not read (verified abstract only) ([arXiv 2610.16426](https://arxiv.org/abs/2610.16426)). A 113-person study found user-written policies blocked 20.1 points less overreach than per-action human approval and 14.5 points less than automated per-action review. Under the policy condition, 133 of the 148 overreach actions that executed ran after a human approved them ([arXiv 2608.27443](https://arxiv.org/abs/2608.27443)). Wu et al. (IEEE S&P 2026) predicted users' permission decisions with **85.1% accuracy using history versus 66.9% without**. That result covers data-access permissions in general agents, so transfer to shell commands is unverified ([arXiv 2511.17959](https://arxiv.org/abs/2511.17959)). LlamaFirewall's AlignmentCheck auditor cut AgentDojo attack success from 17.6% to 2.89%, but the authors note it can itself be prompt-injected ([arXiv 2505.03574](https://arxiv.org/html/2505.03574)).

The notes report one clear absence: **no published work found uses a code graph, call graph or build/test metadata to scope a coding agent's permissions.** The closest are Conseca's directory tree and Claude Code's "packages already in the manifest" allow exception. One 2026 survey of 21 production agent systems found zero production deployment of "intent anchoring" and "trust labeling" ([arXiv 2605.24309](https://arxiv.org/abs/2605.24309)). The notes treat the absence as either a real gap or a search miss. It is not proven.

## Every text-matching and repo-trusting layer has been bypassed

The public failures cluster into five mechanisms, and vendors' own remedies confirm the diagnosis. **Parse divergence** comes first: the checker and the real shell read the command differently. Cursor's CVE-2025-54131 was an allowlist bypass fixed with "a more robust parser" ([GHSA-534m](https://github.com/cursor/cursor/security/advisories/GHSA-534m-3w6r-8pqr)). Codex's CVE-2026-19591 misread PowerShell `--%`, letting a file-writing git command rewrite Codex config and launch an attacker MCP server ([MITRE](https://cveawg.mitre.org/api/cve/CVE-2026-19591)). Tree-sitter treated brace, glob and escape words "as plain words even though the shell changes them at runtime" ([#39159](https://github.com/openai/codex/pull/39159)). Gemini's 2025 "root command" extraction let an approved `grep` chain run an exfiltration command, delivered by injection in a README ([Tracebit](https://tracebit.com/blog/code-exec-deception-gemini-ai-cli-hijack)). Claude Code's own docs list `/bin/rm`, `sh -c` and `git -C` as unmatched spellings ([Permissions docs](https://code.claude.com/docs/en/permissions)).

**State poisoning** makes a later, allowlisted command dangerous. In Cursor's CVE-2026-22708, shell built-ins (`export`, `typeset`, `declare`) ran without checks, so `PAGER` made an allowlisted `git branch` execute attacker code (verified) ([GHSA-82wg](https://github.com/cursor/cursor/security/advisories/GHSA-82wg-qcm4-fp2w); [Pillar Security](https://www.pillar.security/blog/the-agent-security-paradox-when-trusted-commands-in-cursor-become-attack-vectors)). **Trusting repo-controlled config** is the most consequential family. Codex auto-loaded a project's `.env` and `.codex/config.toml`, running MCP server commands on launch (CVE-2025-61260) ([Check Point](https://research.checkpoint.com/2025/openai-codex-cli-command-injection-vulnerability/)). It also ran a crafted `.git/config` `core.fsmonitor` helper outside the sandbox with no prompt (CVE-2026-19592) ([MITRE](https://cveawg.mitre.org/api/cve/CVE-2026-19592)). Gemini auto-trusted folders in headless mode, allowing RCE via a malicious `.gemini/.env`, and under `--yolo` its allowlist was ignored entirely (CVE-2026-12537, critical) ([GHSA-wpqr](https://github.com/advisories/GHSA-wpqr-6v78-jr5g)). **The agent rewriting its own policy** shows up in Copilot's CVE-2025-53773: injected instructions made it write `"chat.tools.autoApprove": true` into `.vscode/settings.json` ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2025-53773)). Finally, **agents treat a denial as an obstacle**. Ona reported Claude Code invoking `/proc/self/root/usr/bin/npx` to dodge a deny rule, then using the unsandboxed retry when bubblewrap caught it (unverified vendor report) ([Ona](https://ona.com/newsletter/03-mar-2026)).

Model judges fail differently: mostly on consent scope, not on recognizing danger. Anthropic's 17% miss rate is dominated by consent mismatch, and conversation-stated boundaries ("don't push") can be lost to compaction ([Permission modes](https://code.claude.com/docs/en/permission-modes)). AuthGateBench finds the mirror image, with models over-blocking authorized actions. The vendors disagree about what a judge should see. Anthropic strips tool results because its ablation showed they hurt. Codex's reviewer reads tool outputs but labels them untrusted. Goose's read-only judge sees only the call. No public evasion study of Claude auto mode, Codex Auto-review, Cursor Auto-review or VS Code Assisted permissions was found, so their adversarial robustness remains **unknown**.

## ACP clients see only the residue each harness lets through

ACP v1 gives a client exactly two levers: answer the requests the agent chooses to send, and pick a mode or config option the agent advertises. A request carries a `toolCall` (`toolCallId`, `title`, `kind`, `content`, `locations`, `rawInput`) and options whose kinds (`allow_once`, `allow_always`, `reject_once`, `reject_always`) are "a hint." The response is only `selected` with an option id, or `cancelled`. There is no reason text, no edited input, and **no schema type for a policy or rule** (verified) ([ACP Tool Calls](https://agentclientprotocol.com/protocol/tool-calls); `acp/schema.py:2331-2345,5482-5500`, agent-client-protocol 0.12.1). The unstable v2 draft drops `session/set_mode` in favor of config options. It also adds a `command` permission subject carrying `command` and `cwd`, which would fix Gemini's missing input if harnesses adopt it ([Session Config Options](https://agentclientprotocol.com/protocol/session-config-options); local `@agentclientprotocol/sdk/schema/v2/schema.unstable.json`).

Three implications follow from the adapters (all verified in local code except where marked). First, **a client that wants to decide per request must select each harness's most-asking mode explicitly**: Claude `default`, Codex `workspace-write` or `read-only`. Even then, self-approved reads and in-sandbox commands never reach it. Second, **`allow_always` is not "remember in the client."** It writes harness-side rules that silently pre-empt the client in later sessions, and the same option kind carries different scopes across adapters, so a policy client must key on `optionId`. Third, no surveyed client applies policy: paseo auto-selects by option kind alone (`paseo/packages/server/src/server/agent/providers/acp-agent.ts:2556-2598,3981-4003`, commit `a1da1b8`). Whether claude-agent-acp forwards the CLI's `decision_reason_type` and `classifier_approvable` fields to a v1 client is unverified, and the presentation code suggests it does not.

Hobbes's own client at commit `38f1e32` has the gaps the notes identify; these were spot-checked for this report. `request_permission` in `pipeline/src/hobbes/providers/acp_session.py:77-92` builds a `PermissionRequest` from only `tool_call_id`, `title` and the options. It **drops the tool call's `kind`, `rawInput`, `content`, `locations` and `_meta`**. The separate `ToolCall` event built from session updates keeps `kind` but not `rawInput` or `locations` (`acp_session.py:106-107`; `events.py:30-36`). The bundled policies choose by option kind only (`events.py:106-123`). Usefully, `allow_all` prefers `allow_once` over `allow_always`, so it does not write harness rules. **Nothing in `pipeline/src/hobbes/providers` calls `set_mode` or `set_config_option`.** So a Codex session runs under Auto-review by default, and a Claude session runs in whatever `permissions.defaultMode` the user's settings name, or `default` if they name none (adapter fallback chain, `claude-agent-acp/dist/session-mode.js:22-35`).

## Where a repo code graph adds signal the field lacks

The evidence points to specific openings rather than a general "smarter judge." Every incumbent mechanism judges the command as written, plus at most CLAUDE.md, README, remotes and recent transcripts. The bypass record is dominated by the gap between that text and what actually executes. A deterministic, provenance-stamped graph of the repo speaks to that gap in four ways. All four are untested design inferences, not results.

**Resolving indirection.** `npm run X`, `make Y`, `./scripts/foo.sh` and `pytest` (with `conftest.py`) all execute repo-controlled code whose body no prefix rule sees. Codex bans `npm run` as a remembered prefix for exactly this reason. VS Code goes the other way and auto-approves scripts defined in `package.json` by default (per release-note summaries; unverified in detail). A graph could map the invocation to the script body or test set it runs, and judge that instead. **Flagging repo-controlled execution.** Git hooks, `core.fsmonitor`, `.env`, and `.codex/`, `.gemini/` and `.claude/` config were the actual CVE vectors. A policy could escalate any command that would read them, and any edit that writes them, rather than trusting a "read-only" label. **Blast radius of in-repo edits.** Claude auto mode never sends in-repo edits or read-only commands to its classifier, yet "commenting out security tests" is one of its block categories. With `tests.json` and `graph.json`, a client could tell when an edit touches test files, security-relevant modules or widely imported interfaces. **Trusted context for consent scope**, the judges' main failure. AuthGateBench found that environment signals improve gate accuracy, and Conseca and Progent generate policy from trusted environment facts. Graph facts are deterministic and not model-written, which makes them a candidate for that trusted slot. Claude's PostToolUse `classifierContext` (capped at 2,000 UTF-16 units, documented as "never a hard boundary") is the one native channel for feeding them to a harness judge (SDK `sdk.d.ts:2689-2695`).

The options for wiring this differ in what they cost and what they can see. **Option A: per-request decider.** Force the most-asking mode and answer every request with a graph-informed policy. This gives Hobbes the most control, but it never sees sandboxed or self-approved actions, and on Gemini it must parse the command from the title. **Option B: residue-only.** Leave harness judges on and apply graph policy only to what they escalate. This is cheap, but the harness decides most actions, and on Codex Auto-review denials never surface. **Option C: compile.** Turn the policy into native rules and hooks (Claude `disallowedTools`/settings hooks, Codex `.rules`/hooks, Gemini `--policy` TOML). This catches actions the client never sees, but it is harness-specific, outside ACP, and inherits each harness's text matching. **Option D: inform the incumbent.** Feed graph facts to the harness's own classifier. This keeps the incumbent's judgment, but the signal is soft and only Claude exposes a channel. These options combine rather than exclude each other.

Several caveats cut against overclaiming. A graph of a hostile repo describes attacker-controlled code faithfully, so "this script only touches `tests/`" is a structural fact, not a safety verdict. Graph-derived trust must not become a new repo-controlled bypass. The graph is a commit snapshot while the agent mutates the working tree, so a script edited earlier in the session may no longer match its extracted body. That ties per-request policy to Hobbes's freshness and snapshot re-extraction work. A graph does not fix shell parse divergence: a faithful parser that refuses to approve what it cannot parse is still required. And narrowing "remember" prefixes is blocked on Codex, which only accepts the harness-proposed amendment verbatim, and on Claude, whose suggestions pass through unchanged. A client that wants narrower memory has to keep its own rule store and answer `allow_once`.

## Conclusion

The field has quietly conceded that per-command approval of text is unsalvageable as a boundary. OpenAI deleted its safe-list, Cursor dropped its denylist, and every major vendor disclaims its judge as a guarantee. Vendors replaced it with sandboxes for containment and model judges for intent. Neither layer reasons about what repo code an approved command will run, or what an in-repo edit touches. That is the unoccupied position. It is also where the worst bugs lived: repo config executing helpers, and allowlisted commands running poisoned scripts. A graph-informed policy is best understood as a resolver that turns a command into the code and files it reaches, feeding whichever decider sits downstream: deterministic rules, a Conseca-style generated policy, or a harness classifier. It does not replace any of them.

For Hobbes specifically, nothing graph-aware is possible yet, because the client discards the inputs and lets the harness choose its own decider. Capturing `kind`, `rawInput`, `locations`, `content` and option ids, and setting modes explicitly, are prerequisites under any of the four options. Which option to pursue, and how to treat `allow_always` and graph staleness, are open decisions for Hobbes's decision records. The notes surface them; they do not settle them.
